- (constraint) Usuaria pediu explicitamente: nao adicionar funcionalidades fora do escopo do PRD sem discutir antes
- (constraint) Nesta etapa nao implementar codigo -- apenas definir e documentar a arquitetura (spine tecnica como unico entregavel, sem doc extra)
- (constraint) Decisoes tecnicas que a UX deixou explicitamente em aberto para a arquitetura (EXPERIENCE.md, DESIGN.md, PRD SS5/9): mecanismo de persistencia das tarefas (PRD Open Question 2/5), risco de perda de dados e mitigacao (PRD SS5, Open Question 5), ordem manual dentro do mesmo nivel de prioridade via drag-and-drop (EXPERIENCE.md Component Patterns/Interaction Primitives), persistencia da preferencia de tema entre sessoes (EXPERIENCE.md Foundation/State Patterns), comportamento em falha ao salvar (EXPERIENCE.md State Patterns -- nota explicita NOTE FOR ARCHITECTURE)
- (direction) Modo escolhido pela usuaria: Coaching path. Entregavel unico: architecture spine tecnica (sem doc de discussao/solution-design extra).
- (constraint) PRD SS5 NFRs: single-user sem login, uso so em navegador desktop (sem mobile/sync no MVP), persistencia deve sobreviver a fechar/reabrir navegador. Non-Goals SS6: sem projetos/categorias/tags/subtarefas, sem colaboracao (nem a longo prazo), sem dashboard/relatorios, sem IA, sem notificacoes/lembretes.
- (decision) Paradigma: TaskFlow MVP e uma SPA 100% client-side, sem backend/servidor. Justificativa: single-user, sem login, uso so em navegador desktop (PRD SS5); nenhuma necessidade concreta de servidor no MVP. Binds: all. Prevents: infra/servidor nao justificado pelo escopo.
- (decision) Persistencia: localStorage do navegador (chave unica, valor JSON serializado com as tarefas + preferencia de tema). Escolhido sobre IndexedDB por ser sincrono, minimo, suficiente para o volume de dados de uma lista pessoal semanal. Binds: FR-1 a FR-7, NFR persistencia (PRD SS5). Prevents: mecanismos de storage divergentes entre features.
- (decision) Mitigacao do risco de perda de dados (PRD Open Question 5): aviso simples e estatico na interface informando que os dados ficam salvos so neste navegador/computador. Sem exportar/importar no MVP -- usuaria decidiu explicitamente nao expandir escopo para isso agora. Binds: NFR persistencia. Prevents: adicionar feature de backup fora do escopo do PRD sem discussao.
- (decision) Comportamento em falha ao salvar (criar/editar/excluir): o Modal de Tarefa permanece aberto, exibe mensagem de erro inline, preserva os dados digitados pela usuaria, e oferece tentar novamente/cancelar. Nunca retry silencioso. Binds: FR-1, FR-2, FR-3. Prevents: perda silenciosa de dados digitados ou falha nao comunicada a usuaria.
- (decision) Stack frontend: Vite + React + TypeScript. Motivo: starter atual bem estabelecido e documentado, ecossistema maduro de bibliotecas de drag-and-drop acessiveis, tipagem ajuda o rigor SDD. Prevents: reimplementar gerenciamento de estado/renderizacao manualmente (vanilla) ou usar ecossistema menor (Svelte) sem necessidade concreta.
- (decision) Gerenciamento de estado: React nativo (useReducer central para acoes de tarefa + Context para expor estado), sem biblioteca externa de state management. Prevents: dependencia e camada extra nao justificadas pelo volume de estado (lista pessoal, usuaria unica).
- (decision) Drag-and-drop: biblioteca dnd-kit (suporte a teclado embutido via keyboard sensor), atende ao Accessibility Floor do EXPERIENCE.md (toda acao de arraste tambem por teclado) sem duplicar logica de interacao. Prevents: implementar e manter duas logicas de interacao (mouse nativo + teclado) separadas.
- (decision) Ordem manual dentro do mesmo nivel de prioridade: campo order (inteiro) por tarefa, escopado a (dia, faixa de prioridade); reindexado sequencialmente ao soltar um card. Preferido sobre indice fracionario por proporcionalidade -- poucas tarefas por dia, sem necessidade de escala tipo Trello. Binds: FR-6, drag-and-drop dentro do dia (EXPERIENCE.md). Prevents: dois componentes assumindo esquemas de ordenacao incompativeis (ex. ordem global vs ordem por grupo).
- (decision) Testes: Vitest + React Testing Library fixados na arquitetura (combinam nativamente com Vite). Prevents: decisao ad-hoc de ferramenta de teste na etapa de historias/dev.
- (decision) Deploy/ambiente: MVP roda so localmente via servidor de dev do Vite (npm run dev, localhost). Sem build de producao fixado nem hospedagem no MVP. Prevents: adicionar pipeline de deploy/CI nao justificado pelo escopo (uso pessoal, um unico computador).
- (decision) Persistencia refinada: duas chaves de localStorage separadas -- 'taskflow:tasks' (envelope { schemaVersion, tasks: Task[] }) e 'taskflow:theme' (string 'light'|'dark') -- porque tarefas e tema sao dominios independentes com gatilhos de mutacao independentes; uma chave unica acoplaria os dois. schemaVersion incluido no envelope de tasks para permitir migracao futura sem redesenho.
- (decision) Atomicidade estado/persistencia: uma mutacao (criar/editar/excluir/mudar estado/reordenar) so e aplicada ao estado React depois que a escrita no localStorage tiver sucesso (tentativa sincrona, try/catch). Se falhar, estado nao muda e o erro sobe para a UI que iniciou a acao (ex. Modal de Tarefa), preservando o que a usuaria digitou -- implementa a decisao de falha ao salvar (modal com erro, dado preservado) sem risco de estado e storage divergirem.
- (decision) Regra de dependencia entre camadas: Componentes (UI) -> State layer (actions/reducer/Context) -> Storage adapter -> localStorage. Componentes nunca importam o storage adapter diretamente; storage adapter nunca importa React/componentes. Somente o storage adapter toca window.localStorage.
- (decision) IDs de tarefa: crypto.randomUUID() (API nativa do navegador), sem biblioteca de uuid externa -- proporcional, evita dependencia desnecessaria.
